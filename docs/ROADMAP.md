# Roadmap

Everything runs on a laptop first (VS Code + browser). Hosting comes later.

| Chunk | Contents | How you test it |
|---|---|---|
| 1 ✅ | Monorepo, event schema v1, `@abigaail/core` fail-open SDK | `npm run check` |
| 2 ✅ | `@abigaail/store` (SQLite) + ingest server | `npm run dev:server`, curl a batch |

| 5b ✅ | Live view (SSE on a loopback listener 127.0.0.1:4320, relayed by the dashboard), Findings, Agents; Usage numbers on the App page (a dedicated Usage view comes later) | Set the same `ABIGAAIL_LIVE_TOKEN` (`openssl rand -base64 32`) for `npm run dev:server` and `npm run dashboard`, run `npm run demo:node`, open an app's Live tab and browse the demo (events appear after the SDK's 5 s flush); then Findings and Agents |

## Phase 2, in chunks

Order is the owner's choice (DECISIONS #86): retention and alerts are pulled forward
from spec phases 4 and 3, then the scrubber, then agents 4-7, each planned against
[AGENTS.md](AGENTS.md).

| Chunk | Contents | How you test it |
|---|---|---|
| 7 ✅ | **Retention**: per-table periods (env, safe minimums), hourly batched deletion in the server for every app with rows (5-min catch-up runs while behind), physical erasure (secure_delete, one-time incremental auto_vacuum conversion when disk allows, WAL truncate), "Data kept" on the dashboard, README periods, Watchdog `retention_behind` and `vacuum_pending` | `npm run check`; sim database with `ABIGAAIL_RETAIN_EVENTS_DAYS=7`, dashboard Agents → "Data kept", `npm run findings` |
| 7b ✅ | **`app:purge`**: delete one app's data on request (GDPR deletion path) while the server runs: disabled apps only, name typed again, `--dry-run`, audited (counts only); batched and resumable; every app_id table covered (static test); alert messages deleted or rewritten, and re-read before every send; late writes for a purged app dropped; Abigaail's findings naming it deleted; a VACUUM at the next start erases the last copies (`erasure_pending` until then). After the owner's test: totals over every run in the audit (`resumed`), Ctrl-C audited as `app.purge_interrupted`; a **weekly full VACUUM** at the quietest hour so deleted data leaves the file within 7 days (`vacuum_skipped` without room, `erasure_overdue`) | `npm run dev:server` + `npm run demo:node`, browse; `npm run app:disable -- demo`; `npm run app:purge -- demo --dry-run`; `npm run app:purge -- demo`, Ctrl-C midway, run again; dashboard: app gone, `erasure_pending` under Abigaail itself; restart `dev:server` (log: "VACUUM after app:purge"), warning gone; Ctrl-C a purge and run it again: `app.purge` totals = all rows, `resumed: 1`; a week on, the log shows "weekly VACUUM in N ms" |
| 8 ✅ | **Alerts**: confirmed red only (critical 2 runs in a row, now also the status rule), from the server process; one webhook (json/slack/discord/ntfy, HMAC-signed, URL rules with a private-network opt-in) and email (nodemailer, STARTTLS required); persisted dedup, 30-min cooldown, grouping, hourly cap, one recovery notice; bounded retries; Watchdog `alert_delivery_failed`; heartbeat URL; `npm run alerts:test`; Alerts page | `npm run check`. Copy `apps/server/.env.example` to `apps/server/.env`, set a webhook (e.g. an ntfy topic) and/or SMTP, plus `ABIGAAIL_DASHBOARD_URL`; `npm run alerts:test`; then `npm run dev:server` and `npm run demo:node`, open `/dependency-down` in a browser ~10× within a minute and again a minute later: one red message within about 2 min, one resolved message about 5-8 min after you stop; dashboard → Alerts and Findings. Stop the receiver (or point the webhook at a dead port) to see retries and `alert_delivery_failed` (through the other channel, or on the dashboard only with one). The simulator's server gets no alert settings (DECISIONS #78) |
| 9 ✅ | **Allowlist scrubber + privacy tests**: error messages (and one level of cause) through a shared, versioned, fail-closed scrubber in the SDK and again on the server; codes by pattern only, outbound `error_code`; hostnames only if the app calls them; the route heuristic fails closed; property, corpus, end-to-end and mutation tests; errors on the App page and in Live (DECISIONS #101-#108) | `npm run check`. `npm run dev:server`, `npm run demo:node`, open `/boom` and `/fetch-error`, then `npm run events:tail -- demo` and the dashboard's App page (Errors) and Live view: "Order failed for `<email>` …" and "fetch failed" with cause ECONNREFUSED. A path with no pattern such as `/users/jane` shows as `/users/[id]` in Live |
| 10a ✅ | **Agent 4, Resilience** and runtime signals: features announced by the server (`runtime_v1`, old servers lose nothing); post-GC heap floor, GC, external memory; the route that blocks the event loop (charged in the SDK, streams never); startup time; opt-in crash record; restarts moved from Health, paired per instance, each with its cause; leak = rising floor; cold start; Health folds lag, a blocking route's latency and RSS into them; **Runtime** tab; blocks in Live; sim scenarios `blocking-route`, `oom-loop`, `leak` (DECISIONS #110-#116) | `npm run check`. Stop `dev:server` and the demos, then `npm run sim -- run blocking-route`, `npm run sim -- run crash-loop`, `npm run sim -- run oom-loop` (each about 25-40 min; PASS/FAIL per finding), watching the dashboard's Runtime tab with `ABIGAAIL_DB_PATH=./data/sim/abigaail.db`. Optional: `npm run sim -- run leak` (about 4 h). By hand: `npm run dev:server` + `npm run demo:node`, open the app's Runtime tab: memory lines and a startup time appear within a minute |
| 10b ✅ | **Continuous profiling** (opt-in `ABIGAAIL_PROFILING=1`, kill switch `off`, `profile_v1`): CPU windows (20 s every 5 min at 10 ms, started only when no request is in flight; each start pauses the app 19-75 ms, measured, budgeted at 60 ms, reported as `profiler_pause_ms` and never counted as a block or lag) per route when unambiguous and inside event-loop blocks, sampling heap profiler (heap snapshots deferred, #116); work budget with back-off, off after 3 overruns, fail-open; `profiles` table, 7 days; top functions, flame graph, block functions and growing heap sites on the Runtime tab; findings name the function and file:line; `npm run bench:profiling`; oom-loop's leak per second (traffic-independent); memory chart zooms to short histories (DECISIONS #118-#122) | `npm run check`. `npm run sim -- run blocking-route` (finding says "Mostly in renderDocs"), `npm run sim -- run oom-loop` ("allocated in rememberSearch"); Runtime tab → Profiles. By hand: `ABIGAAIL_PROFILING=1 npm run demo:node`, browse it for a few minutes, Runtime → Profiles. `npm run bench:profiling` |
| 11a ✅ | **Agent 5, Rollout Safety** and **deploy metadata** (`deploy_v1`: commit, previous release, lockfile hash from the deploy step, held until announced and never dropped, independent of runtime signals): the release's own rows since its deploy against the same hours before it, exact tests corrected for every test and every look, effect and evidence gates; new error types, routes newly returning 404/5xx, routes gone quiet, crash loops after a deploy; "recommend rollback" only with measured high impact and high confidence, held 2 runs; Health and Resilience fold into it once it reports at least as severely, Health judges route errors only since a deploy in its window, a cold start must be faster afterwards; **Releases** tab; README on deploy metadata and source maps; sim scenarios `bad-deploy`, `slow-deploy`, `clean-deploy`, `crash-deploy` (DECISIONS #130-#135) | `npm run check`. Stop `dev:server` and the demos, then `npm run sim -- run bad-deploy`, `slow-deploy`, `clean-deploy`, `crash-deploy` (each about 35-65 min; PASS/FAIL per finding), watching the app's Releases tab with `ABIGAAIL_DB_PATH=./data/sim/abigaail.db`. By hand: `npm run dev:server`, then `ABIGAAIL_RELEASE=$(git rev-parse HEAD) ABIGAAIL_PREVIOUS_RELEASE=$(git rev-parse HEAD~1) ABIGAAIL_LOCKFILE_HASH=$(sha256sum package-lock.json \| cut -d" " -f1) npm run demo:node`, browse, restart it with another release: Releases shows commit, previous and lockfile |
| 11b | **Code-aware findings**: source maps in the SDK (opt-in), an optional read-only GitHub link (one repo, contents:read, api.github.com only, cached, works with GitHub down), release → diff → file/line for new errors, blocks and leaks; paths, line ranges and links only, never code (#92) | Planned (chunk 11 plan) |
| 12 | **Agent 6, Privacy Auditor**: scans stored values (emails, IPs, tokens, JWTs, phone numbers, IBANs, name-like route segments); re-scrubs stored messages with today's rules (a value that changes is a finding, re-scrubbed in place and counted; an old `scrub_version` alone is not), reports `scrub_mismatches` and version drift as counts (#107); verifies retention ran and `salt.bin` ≤ 1 day old, re-identification suppression | Planned against AGENTS.md |
| 13 | **Agent 7, Outbound Dependencies**: per-host normals, first-seen host, retry storms, N+1 per inbound request; **database insight**: query fingerprints with every value stripped, slow queries, N+1 queries, pool use (closes the DB query timing / pool data gap, #92) |
| 14 | **Background jobs, queues and cron**: runs, failures, duration and missed schedules (#92) | Planned against AGENTS.md |
| 15 | **Cross-service tracing**: one request followed across the owner's services (#92) | Planned against AGENTS.md |
| 16 | **AI investigator** (last): off by default; sends findings, metrics and code only, never event rows, to the Claude API or a self-hosted model; suggestions and draft PRs only (#92) | Planned against AGENTS.md | Planned against AGENTS.md |

Everything above stays read-only towards monitored apps (#92).

Later phases follow the spec: agents 8-16, backups, packaging, hosting. **Runtime security**
(loaded packages, reachable CVEs, new outbound hosts) is built with the Security (11) and
Supply Chain (13) agents (#92). An enterprise tier (SSO, roles and teams, Postgres/ClickHouse
+ HA, SIEM audit export, data residency and compliance reports, support) comes later and is
not on this roadmap yet (#93).
