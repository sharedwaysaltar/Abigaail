adding a new entry that supersedes it.

| 2 | Build and test on a laptop first; hosting decided later. | Owner's choice. |
| 3 | `dev` is the single source of truth; `main` only receives tested chunks via PR. | Owner's choice. |
| 4 | Abigaail is designed independently of The Well's repo. Target apps are assumed to be long-running Node processes; serverless is a separate adapter. | The Well repo is out of date (it now runs on a droplet, not Vercel). |

| 8 | Client IP and user agent travel once in a `transient` field; ingest uses them in memory for geo, bot class and the visitor hash, then discards them. | 9 | Request capture via Node `diagnostics_channel` (`http.server.*`, `undici:*`, `http.client.*`). | Read-only, no monkey-patching, works across Next/Express/Fastify. Lesson 4. |

| 11 | Server runs as two processes: `server` (ingest, SSE, scheduler, alerter) and `dashboard` (read-only). Agents each run in a `worker_thread` with a hard timeout. | Lessons 2 and 10: alerts survive the dashboard being down; a looping agent is terminated. |
| 12 | Until the Phase 2 scrubber exists, no free text is sent at all. | Lesson 3, applied before the scrubber lands. |
| 13 | A 401/403 from ingest trips the SDK circuit breaker. | A wrong key should back off, not retry every flush. |
| 14 | Libraries live in `packages/`, runnable services in `apps/` (`apps/server`, later `apps/dashboard`). | Keeps publishable libraries apart from deployables; matches the original layout. |
| 15 | Ingest uses plain `node:http`, no framework, no new dependency. No CORS headers until the browser adapter needs them. | Minimal dependencies; one route does not need a framework. |
| 16 | Ingest keys are `abk_` + 32 random bytes (base64url), shown once, stored only as SHA-256. `app:disable` revokes a key (ingest returns 403). | Lesson 4. The fixed prefix lets the Config & Secrets agent spot a leaked key. |
| 17 | Visitor hash = HMAC-SHA256(key = day salt, `app_id` + IP + UA), truncated to 16 bytes. The IP comes only from `transient.ip`, never from the socket (that is the app server's address). The salt day is the UTC date of receive time. Today's salt is persisted so a restart keeps hashes stable; earlier salts are deleted. Refines #8. | Including `app_id` stops a visitor being linked across tenants (lesson 9). |
| 18 | Batches carry an optional `sent_at` (client clock, per send attempt). Event time = `received_at - clamp(sent_at - client_ts, 0, 24h)`; `received_at` is stored too. | Delayed retries do not show up as fake spikes, and only client-clock differences are used, so a skewed clock is harmless. Additive and optional, so still schema v1. |
| 19 | One invalid event rejects the whole batch. | Simpler and safer than partial acceptance: a misbehaving SDK is visible at once and nothing doubtful is stored. |
| 20 | Ingest hardening: header/request timeouts (10s/15s, checked every 2s), 16 KiB header cap, body cap enforced from `content-length` and while streaming, and any rejection before the body is read closes the connection. Per-app rate limit, plus one global limit on bad-key requests. | Slow or oversized clients cannot tie up ingest; key-guessing floods are cheap to refuse. |
| 21 | Admin actions (app create, app disable) are written to `audit_log`. | Lesson 4. |
| 22 | Deferred: geo lookup (columns reserved), SSE (Chunk 5, with the Live view), `findings`/`agent_runs` tables (Chunk 4, as a migration). `apps.last_event_at` is added now for the Watchdog. | Build what the current chunk needs; migrations add the rest when the shape is known. |
| 23 | Salt erasure is physical, not just logical: the store runs `PRAGMA secure_delete = ON` and checkpoints (truncating the WAL) after every salt rotation. The server rotates the salt at each UTC midnight on an unref'd timer, even when no requests arrive. Refines #17. | A deleted row otherwise lingers in free pages and in the WAL file, and with no traffic yesterday's salt would survive until the next request. Either would let old visitor hashes be recomputed. |
| 24 | The visitor-hash salt lives only in `data/salt.bin` (`ABIGAAIL_SALT_PATH`), never in the database, so the WAL and database backups can never hold it. Format: 10-byte ASCII UTC day + 32 random bytes; mode 0600; created with `wx+` (parent directory fsynced); rotated at startup if the day differs and at each UTC midnight by overwriting those 42 bytes in place (r+, offset 0, fsync), never truncating or replacing the file. An invalid or partial file gets a fresh salt; bytes past 42 are ignored. Rotation zeroes the previous salt in memory. If rotation fails while running, events are still accepted with a null visitor hash (logged once) rather than hashed with a stale salt. Migration 2 drops the old `salts` table, then the store runs VACUUM and a checkpoint, because rows deleted before `secure_delete` was enabled survive in free pages. Supersedes the salt storage parts of #17 and #23. **Limit:** overwriting in place cannot reach SSD wear-levelling copies or filesystem journal/copy-on-write remnants; the server must use full-disk encryption (see [HOSTING.md](HOSTING.md)). | A small file keeps the salt out of every database copy; in-place overwrites are the most software can do for erasure. |
| 25 | The SDK cleans or drops every event before queuing (`sanitizeEvent` in core). Each event is rebuilt from its type's named fields, and values are checked against the patterns ingest uses, which now live in the zero-dependency `@abigaail/schema` index and are shared with `validate.ts`. Repairs: an invalid route becomes `other`, an invalid error class becomes `Error`, an IP-literal outbound host (v4 or v6) becomes `ip-literal`, any other invalid host becomes `invalid-host`, frames with invalid paths are removed, an invalid referrer is removed, the UA is truncated to 512 characters, and an IPv4-mapped IP is unmapped. Anything else invalid drops the event and counts it in `stats().invalid`, which the adapters report as part of `sdk_dropped_events`. Core has no `node:` imports. | Because of #19, one bad event would otherwise lose its whole batch. Client and server share one source of truth for what is allowed. |
| 26 | `@abigaail/node`: inbound requests are captured via `diagnostics_channel`. A 404 reports the route `unmatched` only when no known pattern matches (a 404 on `/user/[id]` keeps that pattern). The default `ignore` list is `/_next/static/*`, `/_next/image`, `/favicon.ico` and `/robots.txt`. Byte counts come from `content-length` only, and the referrer is reduced to its hostname. | Scanners cannot fill the route cap, and asset noise is not traffic. Bodies are never read. |
| 27 | Request flags are checked on only the first 2 KB of path + query, with substring tests only (no regexes that can backtrack) and one percent-decode inside try/catch. Only the flag name leaves the app. | A huge or malformed URL costs the host app nothing. |
| 28 | `trustProxy` (number of reverse proxies) defaults to 0, which uses the socket address. If requests then arrive from a loopback or private address, the SDK reports once through `onInternalError`. Behind Caddy or nginx on the same machine, set `trustProxy: 1`. | A wrong setting either hashes every visitor the same or trusts a spoofable header; the warning makes the first case visible. |
| 29 | Outbound calls are captured from `undici:*` (fetch) and `http.client.*`, host only. Calls to the SDK's own ingest endpoint are skipped. | Telemetry about telemetry would loop. |
| 30 | `init` refuses to start, and reports it, if any `NEXT_PUBLIC_ABIGAAIL_*` variable exists. | Next inlines `NEXT_PUBLIC_*` into browser bundles, so an ingest key there would be public. |
| 31 | Fatal errors are observed only through `uncaughtExceptionMonitor`. The SDK adds no `unhandledRejection`, `SIGTERM` or `SIGINT` listeners. Fatal errors are usually lost, because the process exits before a flush; a crash shows up as a `boot` with no `shutdown` before it. | Adding those listeners would change how the host process behaves (lesson 1). The Resilience agent will read restart patterns instead. |
| 32 | `cpu_percent` = process CPU time (user + system) / wall time × 100 over the metrics interval, so it can exceed 100 when several cores are busy. Event-loop lag subtracts the 20 ms histogram resolution. | Simple and comparable across hosts. Raw histogram readings include the sampling interval. |

Apps import it inside `NEXT_RUNTIME === "nodejs"` and list the `@abigaail/*` packages in `serverExternalPackages`. | The build knows every real route, so nothing else can become a dimension. Keeping the packages external gives instrumentation and handlers one SDK instance. |

| 35 | `react` and `react-dom` (19.3.1): required peers of `next` for the demo. Only `apps/demo-next` depends on them. | Next cannot render without them. |
| 36 | If the ingest endpoint is plain `http://` and its host is not loopback (127.0.0.0/8, `::1`, `localhost`), `@abigaail/node` leaves `transient` out of every event and reports one `AbigaailWarning`. Over https, or http to this machine, it is sent as before. Ingest must be served over HTTPS (see [HOSTING.md](HOSTING.md)). | The visitor's IP and user agent must never cross a network in clear text. Local http keeps laptop development working. |
| 37 | **Traffic that matters** (what Health and Usage count): requests whose `bot_class` is not `crawler`, `ai_crawler` or `automation`, and that carry no `scanner_path` or `injection_like` flag. `unknown` (no user agent, or IP/UA withheld per #36) counts. Counts are weighted by `1 / sample_rate`; percentiles stay unweighted because sampling is uniform. | Owner's choice. Otherwise every app on plain http to another machine would be grey forever. Bots and probes are reported separately, never mixed into health. |
| 38 | Outbound and error events carry an optional `parent_id`: the `event_id` of the inbound request they happened in. `@abigaail/node` picks the request's `event_id` when `http.server.request.start` fires and calls `AsyncLocalStorage.enterWith` (that channel is published synchronously just before `emit('request')`). `linkOutbound` defaults to **true on Node ≥ 24 and false on older Node**, where the SDK reports one `AbigaailWarning` (linking off for performance; set `linkOutbound: true` to enable). Additive and optional, so still schema v1 (as #18). **Benchmark** (`npm run bench`, 16 rounds × 4000 requests, concurrency 32, medians), linking on vs off: **Node v24.16.0** (laptop): a handler that awaits one `fetch`, 3.3-7.0% fewer req/s across four runs (e.g. 3186 vs 3427); a minimal handler, -2.9% to +0.8% (e.g. 14424 vs 14686); bare `enterWith` with no SDK, 1-2%. **Node 22** (owner's run): -10% to -15%. Run-to-run noise is about ±3%. | Closes the AGENTS.md Chunk 4 data gap: Health can name the dependency behind a route's failures. No new identifier leaves the app. Node 24's AsyncLocalStorage (AsyncContextFrame) is cheap enough to default on; Node 22's is not (lesson 1: monitoring must not slow the host). |
| 39 | The linking benchmark is not part of `npm run check` or CI. | Timing assertions flake on shared runners. Correctness of linking (including pipelined requests) is tested in `check`. |
| 40 | **Findings lifecycle.** The runner builds the fingerprint as `agent:signal:subject`. Upsert by (app, fingerprint): `hits` counts runs that emitted it since it opened, `misses` counts consecutive runs that did not. Misses advance **only for apps the agent evaluated successfully in that run**: error, timeout and skipped runs, and apps that threw inside an ok run, never advance them. A finding resolves after 3 misses; one resolved less than 30 min ago is reopened rather than duplicated. **Status per app:** red if an open critical has ≥ 2 hits, amber for any other open critical or warning, grey for an open `unknown` finding or when Health has no good run in 3 min, else green. `info` never changes status. | AGENTS.md: red after 2 runs, recovery after 3 good runs. An agent that cannot see an app must never report it as recovered. |
| 41 | **Agent runner.** Each agent run is one `worker_thread` (memory limits, hard timeout, never overlapping itself: a second start is logged `skipped`). An agent implements `forApp(ctx, app)` and/or `forSystem(ctx)` (the SPEC's `run(ctx) -> Finding[]`, split so each app fails alone). | 42 | **Hourly rollup is the only source of baselines.** `hourly_route_stats` (kind route/host/referrer/error/metric) is filled by the runner in the main thread: each new closed hour re-rolls the last 3 hours (late retries) and missing hours of the last 28 days are backfilled 24 at a time, yielding to ingest between hours. `rollup_hours` marks rolled hours with the app's event count (0 = no data, not zero traffic); `daily_uniques` holds unique humans per UTC day. Agents read raw events only for their 1/5/15-minute windows. Percentiles are nearest-rank. | Raw scans over weeks every minute would grow with traffic. One function computes both windows and rollups, so they cannot disagree. |
| 43 | **Evaluation windows end 45 s before now** (`EVAL_LAG_MS`). | Events still in SDK queues or retries are judged in the window they belong to instead of falling between windows. |
| 44 | Findings about Abigaail itself have `app_id` NULL and are read only through `systemFindings()`. | 45 | `/healthz` answers 503 (body `{ok: false}`, no details) when the Watchdog has not completed a run for 3 min, so the external uptime check also watches the Watchdog. `ABIGAAIL_AGENTS=off` disables the runner and `/healthz` answers 200 `{ok: true, agents: "off"}`. | SPEC lesson 2: something outside must watch the watcher. |
| 46 | Watchdog details: silence threshold = max(3 × the app's median heartbeat gap over 24 h, 3 min). Each system check is guarded on its own; one that throws is reported as `check_failed` and does not hide the others. | Learns each app's rhythm; rotation at midnight is not a false alarm; measured, not guessed. |
| 47 | **Abigaail's own restarts.** For the SDK's longest backoff (5 min, `maxCooldownMs` in core) plus the app's silent threshold after the runner starts, an app that would be "silent" is reported as `reconnecting` (unknown, grey: "waiting for apps to reconnect after Abigaail restarted"), never critical. `agent_stalled` counts from max(last good run, runner start). | 48 | **Fact-style findings.** A finding can be a state rather than a signal (`no_data_yet`, `stopped`, `reconnecting`, `abigaail_down`): stored with `resolves = 'fact'`, it resolves on the first evaluated run where it is no longer true, instead of after 3 misses. Misses still advance only for apps the agent evaluated successfully. Refines #40. | Hysteresis protects against flapping signals; a state that has ended (the app sent its first event, or restarted) has nothing to flap. |
| 49 | **Baselines.** Normal for an hour = the same key at the same hour-of-week over the last 4 weeks when at least 2 of those hours have data; otherwise the same hour on the last 7 days when at least 2 have data; otherwise none, and every finding says which was used. An hour in which the app sent no events at all is "no data" and is skipped, never counted as zero traffic. A route's latency normal is the median and MAD of hourly p95s from hours with ≥ 5 requests. | AGENTS.md principle 1, and honest about how much history exists (principle 5). |
| 50 | **No-baseline fallbacks** (Health), so a new app is not silent while it builds history: 5xx Wilson LB ≥ 5% warning, ≥ 10% critical; route p95 ≥ 2 s warning; dependency failure LB ≥ 10% or p95 ≥ 2 s warning; any error type ≥ 3 times in 15 min warning; event-loop lag and CPU rules are absolute anyway; traffic collapse and the RSS rule do not run. Summaries say "no baseline yet". | Absolute floors only where a value is bad on any app. |
| 51 | **Health folds causes.** When ≥ 50% of a route's 5xx in the judged window made a failed call (error, timeout or 5xx) to the same host, the route's finding is folded into that host's `dependency` finding ("api.stripe.com is failing …, so /api/checkout fails"). A slow route that calls a slow host gets that host as its cause. Linking uses `parent_id` (#38); without it Health still reports both separately. | AGENTS.md: "names the cause, not two alerts". |
| 52 | **Usage findings are `info` and fact-style** (#48): they describe the last completed, rolled-up hour or yesterday, so they resolve as soon as they stop being true, and never change status. Usage reads only the rollup, never raw events. | Usage informs; Health and Watchdog decide status. |
| 53 | Traffic from `curl` and similar clients is `automation` (#37) and never counts towards health. | 54 | **Deploy vs crash.** A `boot` whose release differs from the release of the app's last event before it is a deploy: an info, fact-style `deploy` finding ("deployed release X (was Y)"), never a warning, whether or not a shutdown came first. A boot on the same release with no `shutdown` before it stays the crash `restart` warning. | A deploy that kills the old process is routine; only an unexpected restart deserves attention. |
| 55 | **Unlinked fallback.** Only when linking is off for the app (no outbound event in the window carries a `parent_id`, e.g. Node 22's default, #38): if a failing route has no linked calls but a dependency is failing in the same window, both findings are kept and the route's cause reads "At the same time <host> failed N of M calls; likely related (calls are not linked on this Node version)". Nothing is folded: folding (#51) needs proof through `parent_id`. | Name the probable cause without claiming a link that cannot be shown. |
| 56 | With linking on (some outbound event in the window carries a `parent_id`), a failing route with no linked calls made none, so it gets no dependency cause. Refines #55. | Otherwise a route failing for its own reasons (e.g. `/boom`) would be blamed on an unrelated failing dependency. |
